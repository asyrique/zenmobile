# Zen Mobile — Architecture

Zen Mobile is a companion browser for [Zen](https://github.com/zen-browser/desktop)
on iOS and Android. Its job, in priority order:

1. **Show what's open on desktop**: the tabs on each signed-in Zen/Firefox
   device, and Zen's Spaces, Essentials, pinned tabs and folders, and open any of it.
2. **Be a good mobile browser on its own**, styled after Zen and laid out like
   Arc Search (see [UX.md](UX.md)).
3. **Feed back**: desktop sees this phone's tabs, can send tabs to it and close
   tabs on it.

### Why a Rust core, and why application-services

Firefox iOS and Firefox for Android already share exactly the code we need:
[application-services](https://github.com/mozilla/application-services) is Mozilla's
Rust implementation of Firefox Accounts, Sync 1.5, and the tabs, history,
bookmarks and logins engines, with UniFFI bindings for Swift and Kotlin.
Reusing it means our sync is the same code Firefox ships, not a reimplementation of
hawk auth, scoped-key JWE, collection keys and BSO crypto.

`zen-core` is our "megazord": a single library that links the components we use
plus our own crates. One library means one copy of Rust std, NSS and SQLite, and
`uniffi-bindgen --library` generates one Swift module from it.

Costs we accept:

- **NSS.** application-services' crypto (`rc_crypto`) wraps NSS. It must be built
  per target with `application-services/libs/build-all.sh {ios,android}` and
  linked statically. On Linux dev machines the system `libnss3` works for tests
  (`scripts/env-linux.sh`).
- **Pinned git dependency.** The crates aren't on crates.io. We pin one rev in
  `core/Cargo.toml` and must copy its `[patch.crates-io]` (a uniffi fork).

### What syncs, and where it comes from

| Data | Collection | Written by | Notes |
|---|---|---|---|
| Devices | `clients` | every client | We register as a mobile device so desktop lists us. |
| Open tabs per device | `tabs` | every client | Standard Firefox format: tabs, windows, tab groups. We upload ours too. |
| Spaces, Essentials, pinned tabs, folders, splits, containers | `spaces` | Zen desktop | Zen's own engine (`src/zen/sync/ZenSpacesSync*.sys.mjs`). **Read-only here.** |
| History, bookmarks, logins | `history`, `bookmarks`, `passwords` | Firefox/Zen | Later milestones; same application-services crates. |

The `spaces` engine is **off by default on Zen release builds**: desktop enables
`services.sync.engine.spaces` only on Twilight builds for now, and syncs normal
(unpinned) tabs only with `zen.spaces-sync.normal-tabs`. When the collection isn't
in `meta/global`, sync15 skips our engine cleanly and
`ZenSpacesSnapshot.last_sync_millis` stays `None`; the UI says "Turn on Spaces sync
on desktop" instead of showing an empty sidebar. Open tabs work regardless.

### The `spaces` collection

Each record's cleartext is `{ id, kind, data }`, a projection of desktop's
session store. Kinds: `container`, `space`, `tab`, `folder`, `split` and a singleton
`layout` (space order and Essentials per container). Field-level details live in
`core/zen-spaces/src/record.rs`, which mirrors `ZenSpacesSyncModel.sys.mjs`.

`zen-spaces` keeps a verbatim SQLite mirror of the collection and resolves it on read
into `ZenSpacesSnapshot`: spaces in the user's order, each with a flattened outline
(`rows`, each with a `depth`) of folders, splits and tabs, plus Essentials grouped by
container. Resolution tolerates the half-synced states the server can be in
(dangling ids, items whose parent doesn't list them, folder cycles).

**Why read-only.** Desktop's applier accepts every incoming record as authoritative
(`_reconcile` always returns true) and reconciles it straight into open windows. A
mobile bug that uploaded a stale or partial projection would rearrange or delete
Spaces on every desktop the user owns. Mobile editing (pin a tab, reorder) is a
later milestone and needs a full round-trip test harness against desktop first.

### Accounts

We sign in to Mozilla accounts as Firefox for Android (decision
[0003](decisions/0003-firefox-oauth-client.md)). `zen_fxa_config()` is the only
place that knows this. The OAuth flow runs inside our own web view; the app calls
`zen_parse_oauth_redirect(url)` on each main-frame navigation and, on a match,
cancels it and sends `FxaEvent::CompleteOAuthFlow`. QR pairing with desktop
(`FxaEvent::BeginPairingFlow`, desktop's "Connect another device") uses the same
redirect.

Account state (`FirefoxAccount.to_json()`) holds refresh tokens and the sync key,
so it goes in the Keychain (iOS) or Keystore-encrypted storage (Android), never
`UserDefaults`.

### Sync orchestration

`ZenSyncManager.sync(account, params)` replaces application-services'
`sync_manager`, which can only drive Mozilla's own engines. It fetches the token and
`kSync` from the account itself, runs sync15 over `clients`, `tabs` and `spaces`,
retries once with a fresh token on 401, honours server backoff for non-user syncs,
and returns opaque `persisted_state` for the app to store and hand back.

When to sync: on launch, on foreground (throttled), on pull-to-refresh
(`ZenSyncReason.User`, which ignores backoff), and on FxA push messages (send-tab,
"tabs changed"). Push needs APNs/FCM plumbing and comes in a later milestone.

## Platform notes

- **iOS** must use WKWebView. Content blocking via `WKContentRuleList`.
- **Android** uses GeckoView (decision [0002](decisions/0002-android-geckoview.md)),
  wrapped in a small Kotlin view that Skip embeds. GeckoView adds roughly 60–80 MB.
- **Skip Fuse** compiles our Swift natively for Android with the official Swift
  Android SDK (decision [0001](decisions/0001-skip-fuse.md)). Swift on Android calls
  the same generated UniFFI Swift as iOS, against an Android build of libzen_core.
  Full Skip app builds need macOS + Xcode. Linux can build and test the core and the
  Swift package, and cross-compile the app's Swift for Android with Skip's Linux CLI.
  The Gradle/Kotlin half and iOS need macOS (CI).
